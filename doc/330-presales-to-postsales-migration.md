# Presales → post-sales deploy migration

The runbook for a host that was stood up with `bin/600-bundle-uat` /
`bin/610-deploy-uat` (presales) and is moving onto the `infra/<host>/`
webhook + registry + migrator pipeline (post-sales). **It is a migration,
not a switch:** the two paths use different binary names, role models, env
files and systemd units, and the database changes owner. Decision
(Brandon, 2026-09-21): both paths stay as they are; nothing is
unified in code.

Read `doc/320-presales-uat-deploy.md` (where you are coming from) and
`infra/README.md` (where you are going, including its **one-time host
setup** list, which this doc references rather than repeats).

> Not exercised yet. The first derived app to make this move should correct
> this document as it goes and drop the note.

## Which path am I on?

| Signal on the host | Presales | Post-sales |
|---|---|---|
| API binary | `libexec/api-srv` | `libexec/proto-api` (+ `proto-api.revision`) |
| API env file | `etc/api-srv.env` | `etc/<env>-proto-api.env` |
| Migrator env | none — `610` passes the API env to `proto-migrate` | `etc/<env>-proto-migrate.env` (DDL role) |
| systemd unit | `etc/<SERVICE>.service`, generated by `610` on first run, `User=$SVC_USER` (`www-data`) | `etc/<env>-proto-api.service` shipped from `infra/`, `User=proto`, plus `<env>-proto-restart.{path,service}` |
| Postgres owner of every table | `proto_app` (also the API's login) | `proto_ddl` (migrator only); the API still logs in as `proto_app`, now DML-only |
| How a deploy arrives | tarball in `/tmp`, `sudo ./deploy.sh` | GitHub webhook → `shrmpl-hook` → `bin/uat-proto-build` |
| How the DB changes | wholesale restore of the laptop dump | `proto-migrate verify → pending → pg_dump → up` |
| `/srv/<env>-proto/bin/` | absent | the `infra/<host>/bin/` scripts |

## Names that differ (input to the derivation checklist)

Every name below exists in **both** forms in this repo. A derived app that
renames `proto` → `<app>` must rename it in both places or the migration
below breaks.

| Thing | Presales (`bin/600`, `bin/610`, `etc/uat-deploy.env`, `doc/320`) | Post-sales (`infra/<host>/`, `sql/ddl-role-host-setup.sql`) | Also |
|---|---|---|---|
| API binary | `api-srv` | `proto-api` | locally `bin/100` builds `dist/<slug>-api` (etc/app.env) |
| Migrator binary | `proto-migrate` | `proto-migrate` | same |
| API env on host | `etc/api-srv.env` (from `etc/uat-api-srv.env.example`) | `etc/uat-proto-api.env` | key sets differ — see step 5 |
| Migrator env | — | `etc/uat-proto-migrate.env` | |
| Deploy settings | `etc/uat-deploy.env` → bundle `deploy.env` → host `etc/deploy.env` | `etc/uat-proto-deploy.env` | different keys entirely |
| DML role (API login) | `proto_app` (`DB_APP_ROLE`) | `proto_app` | same role, same password |
| DDL / schema owner | `proto_app` | `proto_ddl` | |
| CI role | — | `proto_ci` | UAT only |
| Group roles | `db_reader`, `db_writer` | `db_reader`, `db_writer` | same (`sql/roles.sql`) |
| Service unit | `$SERVICE` = `uat-proto-api`, generated | `uat-proto-api.service`, shipped | same name, different file |
| Service user | `$SVC_USER` = `www-data` | `proto` | |
| Restart mechanism | `systemctl stop/start` by root | `stg/restart.request` + root-owned `.path` unit | |
| App root | `$APP_ROOT` = `/srv/uat-proto` | `/srv/uat-proto` (`SRV_ROOT`) | same |
| Web root | `web-pub/` | `web-pub/` | same |
| Health | `http://127.0.0.1:$SERVER_PORT/health` (port read from the API env) | `HEALTH_URL` in deploy env | |
| Build machine | laptop, `GOOS=linux GOARCH=amd64` static | the UAT host itself, same flags | |
| Artifact transport | `scp` to `/tmp` | `oras` push/pull, blobs `proto-api`, `proto-web` | |
| Database name | whatever the laptop's `DATABASE_URL` names (`bin/610` reads it from the host's `api-srv.env`) | `uat_proto_db` | |

## Before you start

- Presales host is healthy: `curl -s http://127.0.0.1:<port>/health`.
- The last presales deploy's `db.sql` is the schema you are keeping. From
  here on the database is **persistent**; no more wholesale restores.
- The schema on the host matches migration `0001` (or whatever the latest
  is), because the laptop dump carried `schema_migration` with it. Check:
  `sudo -u postgres psql -d <db> -c 'select * from schema_migration'`.
  If the table is absent, the dump predates the migrator: you will `stamp`
  in step 4.
- The `infra/<host>/` tree has been derived for this app (renamed per
  `infra/README.md` "Deriving an app from this") and every `etc/*.env`
  has been filled on the host — that is `infra/README.md` one-time setup
  step 4, which you can do ahead of time without touching the running
  service.
- You have a maintenance window. Steps 2–7 are downtime.

Run everything as root (`sudo -i`) — the redirects below write to
`/root`; the `sudo -u` prefixes switch to `postgres` / `shrmpl-hook` where
that user must be the one acting. Set these first:

```bash
ENV=uat                         # or prd
APP_ROOT=/srv/${ENV}-proto      # presales $APP_ROOT == post-sales SRV_ROOT
DB=uat_proto_db                 # the database named in etc/api-srv.env
```

## 1. Snapshot (no downtime)

```bash
sudo -u postgres pg_dump -Fc "$DB" > /root/pre-migration-$(date -u +%Y%m%dT%H%M%SZ).dump
sudo cp -a "$APP_ROOT/etc" /root/etc-presales-backup
sudo cp -a "$APP_ROOT/libexec" /root/libexec-presales-backup
```

**State after:** nothing changed; a full rollback point exists.

## 2. Stop the presales unit

```bash
sudo systemctl disable --now "${ENV}-proto-api"
sudo rm /etc/systemd/system/"${ENV}-proto-api".service   # the symlink 610 made
sudo systemctl daemon-reload
pgrep -af libexec/api-srv || echo "no api-srv running"
```

The generated unit file itself stays at `$APP_ROOT/etc/${ENV}-proto-api.service`
until step 6 overwrites it.

**State after:** API down. nginx still serves `web-pub/` (static), `/api/`
returns 502.

## 3. Roles and ownership

`infra/README.md` step 2, done here in full because on a presales host the
schema already has an owner and it is the wrong one.

3a. Cluster roles, as superuser. `db_reader`, `db_writer` and `proto_app`
already exist (bundle `000-roles.sql` created them) and `proto_app` keeps
its name and password — it just stops owning things. Add the two roles
only a post-sales host has (`doc/340-db-host-setup.md`):

```bash
sudo -u postgres psql -v ON_ERROR_STOP=1 <<SQL
CREATE ROLE proto_ddl LOGIN PASSWORD '<generate>';
CREATE ROLE proto_ci  LOGIN PASSWORD '<generate>' CREATEDB;   -- UAT only
REVOKE CONNECT ON DATABASE $DB FROM PUBLIC;
GRANT  CONNECT ON DATABASE $DB TO proto_ddl, proto_app;
SQL
```

3b. Ownership, inside the database. Per object, **not** `REASSIGN OWNED`
(it also tries to move the `public` schema and the database, which
Postgres refuses — see the header of `sql/ddl-role-host-setup.sql`).
`ALTER DATABASE … OWNER` is separate and fine:

```bash
sudo -u postgres psql -v ON_ERROR_STOP=1 -d "$DB" <<'SQL'
DO $$ DECLARE r record; BEGIN
  FOR r IN SELECT tablename    AS n FROM pg_tables     WHERE schemaname='public' LOOP
    EXECUTE format('ALTER TABLE public.%I OWNER TO proto_ddl', r.n); END LOOP;
  FOR r IN SELECT sequencename AS n FROM pg_sequences WHERE schemaname='public' LOOP
    EXECUTE format('ALTER SEQUENCE public.%I OWNER TO proto_ddl', r.n); END LOOP;
END $$;
GRANT CREATE ON SCHEMA public TO proto_ddl;
ALTER DEFAULT PRIVILEGES FOR ROLE proto_ddl IN SCHEMA public GRANT SELECT ON TABLES    TO db_reader;
ALTER DEFAULT PRIVILEGES FOR ROLE proto_ddl IN SCHEMA public GRANT ALL    ON TABLES    TO db_writer;
ALTER DEFAULT PRIVILEGES FOR ROLE proto_ddl IN SCHEMA public GRANT ALL    ON SEQUENCES TO db_writer;
-- existing objects keep the grants 610 gave db_reader/db_writer; nothing to redo
SQL
sudo -u postgres psql -c "ALTER DATABASE $DB OWNER TO proto_ddl"
```

3c. Verify — expect exactly one row, `proto_ddl | <n>`:

```bash
sudo -u postgres psql -d "$DB" -c "select tableowner, count(*) from pg_tables where schemaname='public' group by 1"
```

**State after:** `proto_ddl` owns the schema; `proto_app` can read and
write it (via `db_reader`/`db_writer`) but owns nothing. Nothing to drop:
there is one app role on both paths.

## 4. Bring the database under the migrator

Fill `$APP_ROOT/etc/${ENV}-proto-migrate.env` (`DATABASE_URL` as
`proto_ddl`; `root:shrmpl-hook 0640`). The presales `libexec/proto-migrate`
is fine for this step if the bundle included it; otherwise wait for step 7's
first build and run this then.

```bash
M="$APP_ROOT/libexec/proto-migrate -config $APP_ROOT/etc/${ENV}-proto-migrate.env"
$M status
```

- `schema_migration` present and `status` shows every migration applied →
  done.
- Table absent (dump predates the migrator) and the schema **is** `0001` →
  `$M stamp 1`, then `$M status`.
- `status` shows pending migrations → **stop.** The laptop dump was behind
  `main`. Either `$M up` now (you took the dump in step 1) or sort out why.

**State after:** `$M verify` exits 0, `$M pending` prints `0`.

## 5. Env files

```bash
cd "$APP_ROOT/etc"
sudo mv api-srv.env "${ENV}-proto-api.env"
```

Then diff the keys against the repo's redacted copy. As of 2026-10-02 the
presales example and the post-sales file carry the same key set in a
different order. A host set up from an older example may lack
**`SERVER_BIND_ADDRESS=127.0.0.1`** (without it the API binds every
interface) and still have `JWT_SESSION_EXPIRE_HOURS=72` (now 12). Check
anyway — the two files are maintained separately:

```bash
diff <(grep -oE '^[A-Z_]+=' "${ENV}-proto-api.env" | sort) \
     <(grep -oE '^[A-Z_]+=' /path/to/repo/infra/${ENV}/etc/${ENV}-proto-api.env | sort)
```

Add every key the right-hand side has that the left does not.
`DATABASE_URL` stays as it is: `proto_app` is the API's login on both
paths, and after step 3 it no longer owns the schema. Ownership and mode
per the file header: `root:proto 0640`.

Fill the rest of `infra/README.md` step 4: `${ENV}-proto-deploy.env`,
`${ENV}-proto-test.env` (UAT), `${ENV}-proto-e2e-api.env` (UAT). Delete
the presales `etc/deploy.env` if the host had one; nothing reads it now.

**State after:** `etc/` holds the post-sales set. `api-srv.env` is gone
(backup in `/root/etc-presales-backup`).

## 6. Users, directories, units

`infra/README.md` steps 1 and 5, with the presales leftovers handled:

```bash
sudo useradd -r -s /usr/sbin/nologin -M proto            # if absent
sudo mkdir -p "$APP_ROOT"/{bin,stg,backup}
# the hook swaps web-pub/ in the app root; sticky keeps it off the rest
sudo chown root:shrmpl-hook "$APP_ROOT" && sudo chmod 1775 "$APP_ROOT"
sudo chown -R shrmpl-hook:shrmpl-hook "$APP_ROOT"/{bin,libexec,stg,backup,web-pub}
sudo chown -R www-data:www-data "$APP_ROOT"/log

# binaries: the shipped unit runs libexec/proto-api. Keep the presales
# api-srv as the rollback until step 8; the first webhook build (step 7)
# installs proto-api. Do NOT symlink api-srv -> proto-api: install-api's
# atomic mv would replace the link, not the file, and the .prev logic differs.

sudo cp /path/to/repo/infra/${ENV}/bin/* "$APP_ROOT/bin/" && sudo chmod +x "$APP_ROOT"/bin/*
sudo cp /path/to/repo/infra/${ENV}/etc/${ENV}-proto-api.service \
        /path/to/repo/infra/${ENV}/etc/${ENV}-proto-restart.path \
        /path/to/repo/infra/${ENV}/etc/${ENV}-proto-restart.service "$APP_ROOT/etc/"
# this overwrites the unit 610 generated
sudo ln -sf "$APP_ROOT/etc/${ENV}-proto-api.service"     /etc/systemd/system/
sudo ln -sf "$APP_ROOT/etc/${ENV}-proto-restart.path"    /etc/systemd/system/
sudo ln -sf "$APP_ROOT/etc/${ENV}-proto-restart.service" /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now "${ENV}-proto-restart.path"
sudo systemctl enable "${ENV}-proto-api"      # not started: libexec/proto-api does not exist yet
```

Verify the path unit as the hook user (`infra/README.md` step 5): the
request file must vanish within seconds. The restart will fail (no binary
yet) — that is expected; you are testing the trigger.

```bash
sudo -u shrmpl-hook touch "$APP_ROOT/stg/restart.request"; sleep 3; ls "$APP_ROOT/stg/"
```

**State after:** post-sales units installed and enabled; API still down.

## 7. Webhook, registry, first build

`infra/README.md` steps 6 (nginx — unchanged from presales if it already
proxied `/api/` to `127.0.0.1:$SERVER_PORT`; only the certs script is new)
and 7 (`shrmpl-hook`); install `oras`; fill the registry credentials in
`${ENV}-proto-deploy.env`. Then, rather than waiting for a push, run the
build by hand as the hook user:

```bash
sudo -u shrmpl-hook "$APP_ROOT/bin/${ENV}-proto-build"
```

That runs the tests, builds, pushes to the registry, runs
`${ENV}-proto-install-api` (which does `migrate verify → pending → up` —
expect *nothing pending* after step 4 — installs `libexec/proto-api`,
touches `restart.request`, waits for `MainPID` to change, polls `/health`)
and `${ENV}-proto-publish-web-client`.

**State after:** `libexec/proto-api` running as `proto`, reading
`${ENV}-proto-api.env`, logged in as `proto_app`; `web-pub/`
replaced from the registry.

## 8. Verify

```bash
curl -s "$(sed -n 's/^HEALTH_URL=//p' "$APP_ROOT/etc/${ENV}-proto-deploy.env")"
systemctl show -p MainPID,User --value "${ENV}-proto-api"
cat "$APP_ROOT/libexec/proto-api.revision"
sudo -u postgres psql -d "$DB" -c "select usename from pg_stat_activity where datname='$DB' group by 1"
#   expect: proto_app only (nothing as proto_ddl or postgres)
```

Log in through the web app; on UAT run the suite against it
(`TEST_ENV=... bin/300-run-tests py` from the laptop, or
`${ENV}-proto-run-tests` on the host). Then push a trivial commit to
`BRANCH_TO_CHECKOUT` and watch the webhook do steps 7's build unattended.

Only now, remove the presales binaries:

```bash
sudo rm -f "$APP_ROOT"/libexec/api-srv "$APP_ROOT"/libexec/api-srv.prev "$APP_ROOT"/libexec/proto-migrate.prev
sudo rm -rf "$APP_ROOT/web-pub.prev"
```

`bin/600`/`bin/610` must not be run against this host again: `610` would
`DROP DATABASE` and hand ownership back to `proto_app`. Take
the host out of `etc/uat-deploy.env` (`UAT_HOST`) on every laptop that has
it.

**State after:** migrated. Ordinary operation is `infra/README.md`.

## Rollback

Any point up to step 8, while `libexec/api-srv` still exists:

```bash
sudo systemctl disable --now "${ENV}-proto-api" "${ENV}-proto-restart.path"
sudo rm /etc/systemd/system/"${ENV}"-proto-{api.service,restart.path,restart.service}
sudo cp -a /root/etc-presales-backup/. "$APP_ROOT/etc/"       # api-srv.env, generated unit
sudo ln -s "$APP_ROOT/etc/${ENV}-proto-api.service" /etc/systemd/system/
sudo systemctl daemon-reload
```

Give the schema back (the step 3b block with `proto_ddl` →
`proto_app`, plus `ALTER DATABASE $DB OWNER TO
proto_app`). If a migration ran in step 4 or 7 and you need the
pre-migration schema, restore the step 1 dump instead:
`pg_restore -c -d "$DB" /root/pre-migration-*.dump` as `postgres`.

```bash
sudo systemctl start "${ENV}-proto-api"
curl -s http://127.0.0.1:<port>/health
```

After step 8's cleanup there is no rollback short of a fresh presales
deploy from a laptop (`bin/600` with the step 1 dump loaded locally first).
