# Presales UAT deploy

> **Two deploy paths exist and they are not interchangeable.** This doc is
> the presales one. A host on one path cannot be deployed to with the other's
> tools; moving a host between them is a planned migration
> (`doc/330-uat-postsales-cutover.md`).
>
> | | Presales — **this doc** | Post-sales — `infra/README.md` |
> |---|---|---|
> | Tools | `bin/600-bundle-uat` on the laptop, `bin/610-deploy-uat` as `deploy.sh` on the host | `infra/<host>/bin/*` on the host, triggered by a GitHub webhook |
> | API binary on host | `libexec/api-srv` | `libexec/api-srv` (+ `proto-api.revision`) |
> | API env on host | `etc/api-srv.env` | `etc/<env>-proto-api.env` |
> | DB owner / API login | `proto_app` for both (`DB_APP_ROLE`) | `proto_ddl` owns; API is `proto_app` |
> | Schema change | wholesale restore of the laptop dump | `proto-migrate` on a persistent DB |
> | Unit | generated by `610`, `User=www-data` | shipped, `User=svc-proto`, restart via path unit |
> | Status | **the working deploy today** | placeholder until post-sales |
>
> Tell them apart on a host: `ls /srv/<env>-proto/libexec` —
> `proto-api.revision` means post-sales (both name the API `api-srv`).

## Purpose

A pre-agreement quick deploy for standing a demo/UAT instance up fast: local build +
local Postgres dump replace the UAT server wholesale. There is no webhook, no build
registry, no migrator-driven schema step — the local dev DB dump *is* the UAT DB after
each deploy.

This trades rigor for speed and is meant for the presales phase, before there's a
signed agreement to justify building the full-fat pipeline. Once that exists, the
post-agreement upgrade adds a webhook/registry-driven deploy and a real migrator step
(`proto-migrate`) instead of restoring a dump.

## Server layout

```
/srv/uat-<app>/
  libexec/
    api-srv           # installed by 610-deploy-uat
    proto-migrate      # installed if built into the bundle (used for --no-db verify only)
  web-pub/             # nginx serves this directly
  etc/
    api-srv.env        # written by 610 on the first deploy, secrets generated on the host;
                       # never overwritten, never in the bundle
    uat-<app>-api.service
    nginx-presales_<domain>  # written by 610 on the first deploy, linked as
                       # /etc/nginx/sites-enabled/<domain>; never overwritten
  log/                 # nginx only; API logs to journald
```

`<app>` is `$APP_NAME`, which is `$APP_SLUG` from **`etc/app.env`** (the one place
the app's identity lives — `DERIVING.md`); the systemd unit is `$SERVICE`. Both — and
everything else the two scripts need — come from **`etc/uat-deploy.env`**, committed
and secret-free, which `600` sources after `app.env` so the values below can be
written in terms of `$APP_SLUG`:

| key | side | meaning |
|---|---|---|
| `APP_NAME` | both | `$APP_SLUG` (`proto`); bundle name prefix, unit description |
| `UAT_HOST` | laptop | ssh alias for the UAT host (scp target) |
| `LOCAL_ENV_FILE` | laptop | API env with the inline `DATABASE_URL` to dump. Which server holds it is not in this file: `600` reads `PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD` from **`etc/loc-test.env`** and runs `psql` and `pg_dump` there over TCP, the same address `bin/205` migrated |
| `APP_ROOT` | server | `/srv/uat-$APP_SLUG` |
| `SERVICE` | server | `uat-$APP_SLUG-api` |
| `SVC_USER` | server | `www-data` |
| `DB_APP_ROLE` | server | `${APP_SLUG}_app`; owns the restored DB and is the API's login. Must be a role `src/api-srv/sql/roles.sql` creates (`600` checks) |
| `DB_NAME` | server, first deploy | `uat_${APP_SLUG}_db`; goes into the generated `api-srv.env`, read back from its `DATABASE_URL` after that |
| `UAT_DOMAIN` | server, first deploy | public hostname of the site (`uat-$APP_SLUG.example.com` in the repo: a placeholder, see below); lower-case letters, digits, dots, hyphens (`600` and `610` check) |

`600` sources it (`PRESALES_ENV=<file>` to use another) and stops, naming the key, if
anything is missing — there are no inline defaults — and checks the local database,
`roles.sql` and `DB_APP_ROLE` before the first `go build`, so a bad env fails in under
a second rather than after a minute of building. It writes the six server-side keys
into the bundle as `deploy.env`; `610` (`deploy.sh`) sources that and then
`$APP_ROOT/etc/deploy.env` if the host keeps one, which wins. Same rule: missing key,
no run. This is the same "scripts carry no per-host values" model the post-sales
`infra/<host>/` placeholders use (`infra/README.md`).

`600` also fills the names in `etc/uat-api-srv.env.template` (`DB_APP_ROLE`,
`DB_NAME`, `SERVER_NAME=$SERVICE`, `APP_NAME=$APP_DISPLAY_NAME`) and ships it as
`api-srv.env.template`. It holds no secrets: `__DB_PASSWORD__`, `__JWT_SECRET__`
and `__TOTP_KEY__` stay placeholders until `610` fills them on the host.

## One-time host prep

1. Create `/srv/uat-<app>/{libexec,web-pub,etc,log}`.
2. Nothing to write for the API env: the first deploy writes
   `/srv/uat-<app>/etc/api-srv.env` (root:`$SVC_USER` 0640) from the bundle's
   `api-srv.env.template`, with the DB password, `JWT_SECRET` and
   `TOTP_ENCRYPTION_KEY` each 32 bytes from `/dev/urandom` (64 hex). They reach
   the file through `awk`'s environment, never a command line. Later deploys
   never touch the file; edit it on the host to change a setting.
3. Install nginx (Debian layout, `/etc/nginx/sites-enabled/`) and set
   `UAT_DOMAIN`. The first deploy installs the site (below); once DNS for
   the domain points at the host, run the `certbot --nginx -d <domain>`
   line it prints, once, to add TLS and the port-80 redirect.
4. Install Postgres on the host, listening on `127.0.0.1:5432`.
   `bin/610-deploy-uat` creates the role and database itself (`000-roles.sql` in
   the bundle), then on every run sets `$DB_APP_ROLE`'s password to the one in
   `DATABASE_URL`, fed to `psql` on stdin. The repo literal in `roles.sql` never
   survives a deploy.
5. Optional: `/srv/uat-<app>/etc/deploy.env` with any of `APP_NAME`, `APP_ROOT`,
   `SERVICE`, `SVC_USER`, `DB_APP_ROLE`, `UAT_DOMAIN` to override what the
   bundle carries.

### The nginx site

`600` ships `etc/uat-nginx-site.conf.template` in the bundle. On the first
deploy `610` fills `__UAT_DOMAIN__`, `__APP_ROOT__` and `__PORT__` (`SERVER_PORT`
from the host's `api-srv.env`), writes `$APP_ROOT/etc/nginx-presales_<domain>`
(root 0644), links it as `/etc/nginx/sites-enabled/<domain>`, runs `nginx -t`
and reloads nginx. The site is HTTP only: `root` is `web-pub/`, `/api/` is
proxied to `127.0.0.1:$SERVER_PORT/` (the trailing `/` strips the prefix),
`X-Forwarded-For` is appended to (one hop, `TRUSTED_PROXY_COUNT=1`), the body
cap is 20M, logs go to `log/`, and the security headers sit on the web
locations only, as in the post-sales sites. `certbot --nginx` then edits the
file through the link to add the 443 block and the redirect.

It never overwrites the site file: later deploys print "left alone", so edit
it on the host. It installs nothing, with a note, when `UAT_DOMAIN` is under
`example.com` (the repo's placeholder), when nginx or `sites-enabled` is
missing, or when an enabled site already has `server_name` for the domain (a
host whose site was written by hand keeps it). If `nginx -t` fails with the
new site, `610` unlinks and removes it and stops before touching the service
or the database; fix the cause (a missing `log/` is the usual one) and deploy
again.

### A host set up before 610 generated secrets

Its `api-srv.env` was made by hand and may still carry the repo's public
`roles.sql` password. Rotate it once, as root, then deploy with `--no-db` (which
sets the role to the new password and restarts the API):

```bash
E=/srv/uat-<app>/etc/api-srv.env
grep -c ':reallygoodPSQLpassword@' "$E"     # 1 = still the repo literal
( umask 077
  PW=$(od -An -vtx1 -N32 /dev/urandom | tr -d ' \n') awk '/^DATABASE_URL=/ {
      i = index($0, "//"); r = substr($0, i + 2)
      $0 = substr($0, 1, i + 1) substr(r, 1, index(r, ":")) ENVIRON["PW"] substr(r, index(r, "@")) }
    { print }' "$E" > "$E.new" ) && cat "$E.new" > "$E" && rm "$E.new"
sudo /tmp/<app>_bundle_YYYYMMDD_hhmm/deploy.sh --no-db
```

`cat >` keeps the file's owner and mode. Leave `JWT_SECRET` (rotating it signs
everyone out) and `TOTP_ENCRYPTION_KEY` (rotating it breaks every enrolled
authenticator) unless they are weak.

### A host whose `api-srv.env` predates a required key

Deploys never rewrite `api-srv.env`, so a key the API started requiring after
the host's first deploy is missing there and the new binary exits with
"`KEY` is required". Add it by hand, as root, before deploying:
`LOG_LEVEL=info` (debug, info, warn or error),
`SERVER_BIND_ADDRESS=127.0.0.1` (nginx is the only way in),
`INVITE_TTL_HOURS=72` (hours an invite link works) and
`ALLOW_MFA_EXEMPT_VIA_API=false` (the API refuses to turn `mfaExempt` on;
`true` is for the test harness only). `610-deploy-uat` refuses a file
without `SERVER_BIND_ADDRESS` or `ALLOW_MFA_EXEMPT_VIA_API` before it
stops the service.

## The two commands

```bash
# 1. Local machine — build + bundle + ship
bin/600-bundle-uat                 # build, dump local DB, scp to $UAT_HOST:/tmp/
bin/600-bundle-uat --no-scp        # build only, skip the scp
bin/600-bundle-uat --no-db         # skip the local DB dump (server DB is kept)

# 2. Server — extract + deploy (needs sudo)
cd /tmp && tar xzf <app>_bundle_YYYYMMDD_hhmm.tar.gz
sudo ./<app>_bundle_YYYYMMDD_hhmm/deploy.sh              # replaces DB + binary + web
sudo ./<app>_bundle_YYYYMMDD_hhmm/deploy.sh --no-db      # keep the server's current DB
```

The bundle holds a full `pg_dump` of the local database, so `600` does not
leave it in `dist/`: a successful scp deletes the local tarball (the host
copy in `/tmp` is the one `deploy.sh` runs from); a failed scp keeps it and
prints the `scp` to retry; `--no-scp` keeps it for you to copy and delete.
A failed build removes its staging directory. Every run then names any
earlier bundle still in `dist/` and prints the `rm` for each; it never
deletes one itself.

`610-deploy-uat` first refuses a post-sales host (below), writes `api-srv.env` if
it is missing, installs the systemd unit and the nginx site if they are missing,
then stops the service, optionally drops/recreates/restores the DB
from `db.sql`, sets the role password from `api-srv.env`, installs `api-srv` (and
`proto-migrate`, if it was built into the bundle) into `libexec/`, replaces
`web-pub/`, starts the service, and polls `/health` for 15s.

Because a normal deploy restores the whole local dump, the `schema_migration` table (if
present) travels with it — there is no separate migrate-apply step. When `--no-db` is
used instead, the server's existing DB might be ahead of or behind this build, so the
script runs `proto-migrate -config api-srv.env verify` after installing the binary as a
sanity check (warns, does not fail, if the migrator isn't in the bundle).

## Rollback

Both the binary and the web bundle are kept as `.prev` alongside the live copy
(`libexec/api-srv.prev`, `libexec/proto-migrate.prev`, `web-pub.prev`) after any deploy
that replaces them. To roll back by hand:

```bash
sudo systemctl stop uat-<app>-api
sudo mv /srv/uat-<app>/libexec/api-srv.prev /srv/uat-<app>/libexec/api-srv
sudo rm -rf /srv/uat-<app>/web-pub && sudo mv /srv/uat-<app>/web-pub.prev /srv/uat-<app>/web-pub
sudo systemctl start uat-<app>-api
```

There is no DB rollback beyond re-running a deploy from an older bundle's `db.sql`.

## Post-agreement upgrade

This presales path is intentionally disposable. Once there's a signed agreement, the
next step up is a webhook/registry-driven deploy pipeline with a real `proto-migrate`
apply step against a persistent UAT database, instead of restoring a fresh dump each
time. The placeholder for it is already staged under `infra/{uat,prd}/` — see
`infra/README.md`. **Moving an existing host from this path to that one is a
migration** — binary name, env file, unit, and above all the database's owner all
change — and the ordered runbook, with rollback, is
`doc/330-uat-postsales-cutover.md`; prod is installed fresh, from the same local
dump, by `doc/331-prd-postsales-install.md`. Once a host has been migrated, `610`
refuses it: when `$APP_ROOT/etc/*-<app>-deploy.env` exists (the post-sales deploy
env, e.g. `uat-proto-deploy.env`) it exits 1 before touching anything, since it
would drop the database and hand it back to `proto_app`. `etc/deploy.env`, the
presales override, does not match.
