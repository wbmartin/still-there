# infra/ — host mirrors for the post-sales deploy pipeline

> **PLACEHOLDER — not used until post-sales.** Nothing in here is wired up
> or exercised today. The presales path (`bin/600-bundle-uat` /
> `bin/610-deploy-uat`, see `doc/320-presales-uat-deploy.md`) is the working
> deploy. This tree is staged so that, once a customer agrees and a real
> UAT/prod pair exists, the full-fat webhook + registry + migrator pipeline
> can be brought up by filling in files rather than designing them.
>
> The runbooks: `doc/330-uat-postsales-cutover.md` moves the presales UAT
> host onto this pipeline; `doc/331-prd-postsales-install.md` installs prod
> fresh, from the same local dump; `doc/340-db-host-setup.md` is the
> database setup both use; `doc/350-repository-reset.md` moves the repo
> they deploy from to a new one.

## Which path am I on?

Two deploy paths exist and they are not interchangeable. A host built with
the presales scripts has different env files, units and — the part that
matters — a different Postgres owner. Moving a host from one to
the other is a planned migration: `doc/330-uat-postsales-cutover.md`.

| | Presales — `doc/320-presales-uat-deploy.md` | Post-sales — **this doc** |
|---|---|---|
| Tools | `bin/600-bundle-uat` (laptop) + `bin/610-deploy-uat` (host, as `deploy.sh`) | `infra/<host>/bin/*`, webhook-triggered |
| API binary on host | `libexec/api-srv` | `libexec/api-srv` (+ `.prev`, `proto-api.revision`) |
| API env on host | `etc/api-srv.env` | `etc/<env>-proto-api.env` |
| DB owner / API login | `proto_app` for both | `proto_ddl` owns; API is `proto_app` |
| Schema change | wholesale restore of the laptop dump | `proto-migrate` on a persistent DB |
| Unit | generated by `610`, `User=www-data` | shipped from `etc/`, `User=svc-proto`, restart via path unit |
| Status | the working deploy today | placeholder until post-sales |

Tell them apart on a host: `ls /srv/<env>-proto/libexec` —
`proto-api.revision` means post-sales (both name the API `api-srv`). The
full list of names that differ is in `doc/330`.

## The convention

`infra/<host>/{bin,etc}` mirrors `/srv/<env>-proto/{bin,etc}` on that
server, file for file. Two placeholder hosts are committed:

| Repo dir     | Host path        | Role |
|--------------|------------------|------|
| `infra/uat/` | `/srv/uat-proto` | build host: webhook → tests → build → push → install |
| `infra/prd/` | `/srv/prd-proto` | promotes UAT's digests; never builds |
| `infra/sql/` | — | `proto-host-db.sql`: the three Postgres roles and the database, either host (`doc/340-db-host-setup.md`) |

**The repo is the source of truth for structure; the filled file lives
only on the host.**

- `bin/` scripts are **deployed verbatim** — `cp` to the host, `chmod +x`,
  nothing edited there. They carry no secrets and no per-host values.
  Every script opens the same way: derive `$SRV_ROOT` from its own
  location, take `APP_ENV="$(basename "$SRV_ROOT")"`, `source` its
  `etc/$APP_ENV-*.env`, and die naming the key if any required variable
  is unset. No `${VAR:-default}` fallbacks, ever.
- **Names come from the app root.** Every env file, lock, unit and called
  script is built from `APP_ENV`, so the app root must be named
  `<env>-<slug>` (`/srv/uat-proto`, `/srv/prd-proto`) and the files in it
  carry that prefix. Only the blob and binary names (blobs `proto-api`,
  `proto-web`; binaries `api-srv`, `proto-migrate`) and `*-start` / `*-stop` spell the slug
  literally. A job run on both hosts is therefore **one file copied per
  host dir**: `*-install-api`, `*-publish-web-client`, `*-renew-web-certs`
  are byte-identical across `infra/uat/bin/` and `infra/prd/bin/`. Edit
  one, copy it over the other; `bin/300-run-tests infra` (part of `all`)
  fails when a pair differs.
- **Hook scripts run as `shrmpl-hook`.** `*-build`, `*-install-api`,
  `*-publish-web-client`, `*-promote-uat` and `*-promote-uat-and-deploy`
  re-exec themselves with `sudo -u shrmpl-hook -H` when started as anyone
  else, so an operator's `sudo .../uat-proto-install-api <tag>` writes
  files the next webhook run can replace. `*-renew-web-certs` and
  `*-backup-all` run as root from cron.
- `etc/*.env` holds everything per-host or secret. The repo copy is
  **redacted**: every real value is spelled `SERVERONLY`, hostnames are
  `example.com`. After a PR that touches `infra/<host>/etc/`, diff the
  redacted copy against the host file and carry the change across by hand.
  Never commit a real value.
- `etc/*.service`, `*.path`, `nginx_*` are copied to the host's `etc/` and
  symlinked into `/etc/systemd/system` / `/etc/nginx/sites-enabled`, so the
  unit has one source of truth. The API unit runs as `svc-proto` in the
  app root (`WorkingDirectory`) inside a systemd sandbox: the filesystem
  is read-only to it (`ProtectSystem=strict`, no `ReadWritePaths`; it logs
  to the journal and writes no files), no capabilities, IP and Unix
  sockets only, `@system-service` syscalls. `systemd-analyze security
  <env>-proto-api` on the host scores it.
- `shrmpl-etc/` mirrors `/srv/shrmpl/etc/` — the shrmpl agents' config,
  which sits outside the app root, hence the separate directory. Same
  redaction rule as `etc/`, and the host copy must match what is committed.

  | Repo dir | Agent | One file per |
  |---|---|---|
  | `shrmpl-etc/hooks/` | `shrmpl-hook`: checks the signature against `HOOK_SECRET` and runs `HOOK_SCRIPT` when the push was to a branch in `HOOK_ALLOWED_BRANCHES` | webhook receiver, its id in the filename (`HOOKID`) |
  | `shrmpl-etc/nack-monitors/` | nackmon, a dead-man's switch: the job curls `https://<nackmon-host>/checkin?code=<nackid>` on success and nackmon alerts when nothing arrives within `NACK_GRACE_MIN` of `NACK_CRON` | watched cron job, its check-in code in the filename (`NACKID`) |
  | `shrmpl-etc/pulsecheck-endpoints/` | pulsecheck: polls every `PULSE_INTERVAL_SEC`, alerts on down/up transitions, warns on TLS certs inside 10 days | monitored URL |

  The check-in URL is never hard-coded here: the job reads it from its own
  env file (`HEALTHCHECK_URL` in `etc/prd-proto-backup.env`,
  `CERT_HEALTHCHECK_URL` in `etc/<env>-proto-deploy.env`), so the code
  appears only in a filename. `NACK_CRON` must match the crontab entry that
  runs the job; the grace, escalation and interval values committed here are
  starting points, not measurements.

  **Monitors live on the monitoring host, never the host they watch:** a
  monitor on the host it watches cannot report that host down. A monitor
  file goes in the mirror of the host that runs nackmon and pulsecheck,
  named for the host it watches: UAT's (`uat-proto-*`) are in
  `infra/prd/shrmpl-etc/`, so `infra/uat/shrmpl-etc/` holds only the
  build hook. Prod's own monitors are there too, for want of a third host;
  move them when one exists, since nothing reports prod down until then.

- `fail2ban/` mirrors `/srv/fail2ban/{bin,etc}` — also outside the app root,
  because fail2ban runs once per server and `etc/jail.local` is the single
  file listing every jail on it. `bin/migrate-to-srv-config` is the one-time
  root script that moved the live config out of `/etc/fail2ban/` and left
  symlinks behind, which is what makes `/srv/fail2ban` the copy of record and
  this mirror possible. The convention is **one jail per app**, named after
  the app's `/srv/<app>` directory and watching that app's own nginx access
  log — this repo owns `[<env>-proto]`. On a host shared with other apps the
  live `jail.local` is the union of the jails each app's repo owns; carry a
  change in either direction so the two stay equal. Only `ignoreip` is
  redacted. `findtime`, `maxretry` and `banaction` sit in `[DEFAULT]`, so
  they are the host's values, shared by every jail on it (both hosts run
  `maxretry = 10`). The app jail ignores `/api/` lines: the API answers
  4xx to real users by design, and it rate-limits and locks out failed
  logins itself, so a ban there would only lock real users out.

| Script | Sources | Required keys |
|---|---|---|
| `uat-proto-build`, `-install-api`, `-publish-web-client` | `etc/uat-proto-deploy.env` | registry server + credentials, `SERVICE`, `HEALTH_URL`, `DEPLOY_TAG`, `BRANCH_TO_CHECKOUT`, `REPO_URL`, `BUILD_STG`, `SLACK_WEBHOOK` |
| `uat-proto-run-tests` → `bin/300-run-tests` | `etc/uat-proto-deploy.env` (`BUILD_STG`), then `etc/uat-proto-test.env` via `TEST_ENV` | CI role, scratch DB names, harness paths (same keys as `etc/loc-test.env`) |
| `*-install-api` → `proto-migrate` | `etc/<env>-proto-migrate.env` | the DDL role's `DATABASE_URL` |
| `*-renew-web-certs` (root cron) | `etc/<env>-proto-deploy.env` | `SITE_NAME`, `CERTBOT_EMAIL`, `CERT_HEALTHCHECK_URL` |
| `prd-proto-promote-uat`, `-promote-uat-and-deploy`, `-install-api`, `-publish-web-client` | `etc/prd-proto-deploy.env` | registry server + credentials, `SERVICE`, `HEALTH_URL`, `DEPLOY_TAG`, `PROMOTE_FROM_TAG`, `SLACK_WEBHOOK` |
| `prd-proto-backup-all` (root cron) | `etc/prd-proto-backup.env` (root:root 0600) | `BACKUP_ROOT`, `REMOTE_SERVER`, `REMOTE_DIR`, `DATABASE_NAME`, `HEALTHCHECK_URL` |

`*-start` / `*-stop` are operator tools that call `systemctl` directly; run
them as root. The build never uses them.

## Promotion flow

```
push to BRANCH_TO_CHECKOUT
  → GitHub webhook → shrmpl-hook on the UAT host
  → /srv/uat-proto/bin/uat-proto-build
       flock (waits up to 30 min for a running build; HOOK_TIMEOUT 3600)
       · git reset --hard origin/<branch> · Slack started (full sha)
       · go toolchain check (GOTOOLCHAIN=auto)
       static go build cmd/server + cmd/migrate · vite build + tar
       oras push  proto-api:sha-<commit> + proto-web:sha-<commit>, tag :uat
       uat-proto-install-api    (pull · the incoming proto-migrate, from the
                                 pull dir: verify → pending → pg_dump → up
                                 · swap api-srv + proto-migrate, old as .prev
                                 · restart via path unit · MainPID change
                                 · /health; failure prints the rollback)
       uat-proto-publish-web-client
       Slack deployed, or FAILED at <step> with the full sha (exit 1)
       uat-proto-run-tests      (bin/300-run-tests all, on the deployed
                                 commit; result line in stg/run-tests.result)
       green: tag sha-<commit>-passed on both blobs · Slack tests passed
       red:   Slack tests FAILED, don't promote · the deploy stands (exit 0)

prod: /srv/prd-proto/bin/prd-proto-promote-uat-and-deploy [<commit>]
       prd-proto-promote-uat    retags the UAT digests as :prd — NEVER rebuilds;
                                refuses if api and web revisions disagree, or
                                if sha-<commit>-passed is not on those digests
       prd-proto-install-api · prd-proto-publish-web-client --pull prd
```

UAT deploys before it tests, so a change can be looked at on UAT while
the suite runs, and one flaky test does not hold every deploy back. The
price is that `:uat` can be a red build; the `-passed` tag is what keeps
it off prod.

The hook user (`shrmpl-hook`) has no sudo. Restarting the service is done
by a root-owned systemd **path unit** (`<env>-proto-restart.path`) that
watches `stg/restart.request`; `install-api` touches the file and waits
for `MainPID` to change before polling `/health`.

## Release checklist

Most releases are the flow above: a push, *tests passed*, a promote. A
release that also carries a migration, a host-file change or anything
else worth a planned rollback gets a written record: copy this skeleton
to wherever the app tracks the work (the pull request description, say),
fill it before starting, and tick it as it runs. Every project will be
different; the letters are the shape, not a fixed list. Every host
block:

- opens with `hostname`, so the first line of output names the host the
  paste landed on;
- names literal paths, or writes each variable set in an earlier block as
  `${VAR:?}` inside every command that uses it. A `: "${VAR:?}"` line on
  top is not enough: an interactive shell aborts only the line that
  fails, and the next pasted line runs with the variable empty
  (`"$APP_ROOT/etc"` becomes `/etc`);
- puts `sleep 2` between `systemctl reload nginx` and a `curl` check: the
  old workers keep answering until they drain, and a curl in the same
  paste reads the old site.

**P. Pre-flight**

- [ ] What ships, by layer: code (the registry build), schema
      (`git diff --stat <prod-commit>..<release-commit> --
      src/api-srv/sql/migrations`), host files (the same over `infra/`),
      data (normally none).
- [ ] Rollback targets, full shas: on each host
      `cat /srv/<env>-proto/libexec/proto-api.revision`.
- [ ] Freeze: no other push to `BRANCH_TO_CHECKOUT` (or the prod release
      branch) until R.
- [ ] A migration ships: a prod backup by hand first
      (`/srv/prd-proto/bin/prd-proto-backup-all` as root, `doc/331` B2);
      `install-api` also dumps to `backup/` before `up`.
- [ ] A new or tightened required config key ships: env files are never
      overwritten by a deploy, and the API refuses to start on a missing
      or malformed key. Check each host's env file first (both API env
      files, and UAT's `uat-proto-e2e-api.env`), printing presence and
      lengths, never a value. As root on the host, naming the release's
      keys:

      ```bash
      hostname
      awk '{ k = substr($0, 1, index($0, "=") - 1); v = substr($0, index($0, "=") + 1) }
        k == "JWT_SECRET" { print k " length " length(v) "  (need >= 32)" }
        k == "TOTP_ENCRYPTION_KEY" { print k " length " length(v) (v ~ /^[0-9a-fA-F]+$/ ? " hex" : " NOT HEX") "  (need 64 hex)" }
        k == "NEW_KEY" { print k " present, length " length(v) }
      ' /srv/prd-proto/etc/prd-proto-api.env
      ```

      A key that prints nothing is absent: add it to that host's file by
      hand before the release reaches that host.

**A. Approvals**: who signs off the merge, the UAT look and the promote,
with the date, recorded beside each step.

**U. UAT**

- [ ] Merge to `BRANCH_TO_CHECKOUT`. Slack *started*, *deployed*, *tests
      passed*, each with the release commit's full sha.
- [ ] `curl -fsS https://<uat-site>/api/health`; `proto-api.revision`
      names the release commit.
- [ ] Host files under `infra/uat/`: moved as below, the source being the
      build checkout (`BUILD_STG`), already at the deployed commit.
- [ ] The release's own checks, in a browser.

**R. Prod**

- [ ] Promote by full sha (`doc/331` Every later release):
      `sudo -u shrmpl-hook -H
      /srv/prd-proto/bin/prd-proto-promote-uat-and-deploy <full sha>`.
- [ ] Health and `proto-api.revision` as on UAT (`installed_tag=prd`).
- [ ] Host files under `infra/prd/`: the `git archive` in `doc/331` Every
      later release, or one file moved as below.
- [ ] The release's own checks; lift the freeze.

**Rollback, per host**

- Code, no migration between: promote the recorded prod sha again; its
  `sha-<commit>-passed` tag still stands. A failed health check right
  after an install prints the `.prev` swap to run.
- Code across a migration: restore the pre-migrate dump in `backup/`;
  `proto-migrate verify` refuses an older binary on a newer schema, so a
  re-promote is not a rollback.
- UAT: push a revert; a by-hand install is replaced by the next push.
- A host file: its `.before` copy back, then the same test and reload.

**Moving one host file, hash-checked.** Prod has no checkout, so a file
goes over by itself, from a pushed commit, never the working tree. `F` is
its path under `infra/prd/` (`bin/...` or a unit in `etc/`); on the host
it is the same path under `/srv/prd-proto/`. Locally:

```bash
: "${PRD_SSH:?}" "${F:?}"
N=${F##*/}
git fetch origin
git show "origin/main:infra/prd/${F:?}" > "/tmp/${N:?}"
shasum -a 256 "/tmp/${N:?}"
scp "/tmp/${N:?}" "${PRD_SSH:?}:/tmp/" && rm "/tmp/${N:?}"
```

On prod as root, with `F` set again:

```bash
hostname
: "${F:?}"
N=${F##*/}; T=/srv/prd-proto/${F:?}
sha256sum "/tmp/${N:?}"
diff "${T:?}" "/tmp/${N:?}"
cp -p "${T:?}" "/root/${N:?}.before"
cp "/tmp/${N:?}" "${T:?}" && rm "/tmp/${N:?}"
```

The hash matches the local one and `diff` shows only the intended change.
`cp` onto the existing file keeps its owner and mode. A unit then needs
`systemctl daemon-reload` (a changed API unit takes effect at the next
`systemctl restart prd-proto-api`). If it goes wrong,
`cp -p "/root/$N.before" "$T"` and reload again. Three files do not move
this way: an env file (a new key is added to the host's file by hand),
the nginx site (rendered with the real site name, `doc/331` Every later
release, then `nginx -t` before the reload) and `jail.local` (merged with
the other apps' jails, step 8, then `fail2ban-client -t`). Each keeps the
`.before` copy and the test before the reload.

**Running host SQL, hash-checked.** SQL a host runs by hand (roles and
grants, `infra/sql/proto-host-db.sql`; never a schema change, which is a
migration) goes over the same way, from a pushed commit, with a backup
first and a rollback statement written down before it starts. `S` is its
repo path. Locally:

```bash
: "${PRD_SSH:?}" "${S:?}"
N=${S##*/}
git fetch origin
git show "origin/main:${S:?}" > "/tmp/${N:?}"
shasum -a 256 "/tmp/${N:?}"
scp "/tmp/${N:?}" "${PRD_SSH:?}:/tmp/" && rm "/tmp/${N:?}"
```

On prod as root, with `N` set again. First the hash and the backup:

```bash
hostname
sha256sum "/tmp/${N:?}"
/srv/prd-proto/bin/prd-proto-backup-all; echo "backup exit $?"
```

The hash matches the local one and it prints `backup exit 0`. Anything
else: STOP here, and paste nothing further. Then apply, verify, clean up:

```bash
hostname
sudo -u postgres psql -X -v ON_ERROR_STOP=1 -d prd_proto_db < "/tmp/${N:?}"
sudo -u postgres psql -X -d prd_proto_db -c '<the query that shows the change>'
rm "/tmp/${N:?}"
```

`proto-host-db.sql` itself takes its database and passwords as `\set`
lines on stdin: its apply line is the `doc/340-db-host-setup.md` block,
with `SQL` set to `/tmp/$N`. The record carries the one statement that
undoes the change (a `REVOKE` for a `GRANT`, say), run the same way if a
check after it fails; a change that one statement cannot undo is a
restore of the backup.

## Layout on the host

```
/srv/<env>-proto/                                 (root:shrmpl-hook 1775)
├── bin/         copies of infra/<host>/bin/      (shrmpl-hook:shrmpl-hook)
├── etc/         filled env files, units, nginx   (root:<group> 0640)
├── libexec/     api-srv, proto-migrate (+ .prev), proto-api.revision
├── stg/         build output, pull dirs, restart.request, test logs
├── backup/      pre-migrate pg_dump -Fc files
├── crt/         TLS certs placed by *-renew-web-certs
├── log/         nginx access/error logs (the API logs to journald)
│                                                 (www-data:www-data)
└── web-pub/     the extracted React bundle — what nginx serves
                                                  (shrmpl-hook, a+rX)
```

The publish swaps `web-pub/` by creating and renaming entries in the app
root as `shrmpl-hook`, hence group write on the root. The sticky bit (the
`1` in 1775) lets the hook rename or delete only entries it owns, so
root's `etc/` and `crt/` and www-data's `log/` stay out of its reach.

## One-time host setup (the checklist the runbooks follow)

All as root, once per host. The paste-ready steps, with checks and
rollback, are `doc/330-uat-postsales-cutover.md` (UAT, from a presales
host) and `doc/331-prd-postsales-install.md` (prod, fresh); this list is
what they do.

1. **Users and dirs.** `useradd -r -s /usr/sbin/nologin -M svc-proto`;
   `mkdir -p /srv/<env>-proto/{bin,etc,libexec,stg,backup,web-pub,log}`;
   `chown root:shrmpl-hook /srv/<env>-proto && chmod 1775
   /srv/<env>-proto`;
   `chown -R shrmpl-hook:shrmpl-hook .../{bin,libexec,stg,backup,web-pub}`;
   `chown -R www-data:www-data .../log`. `stat -c '%U:%G %a'
   /srv/<env>-proto` must print `root:shrmpl-hook 1775`. On UAT also the
   checkout at `BUILD_STG`, owned by `shrmpl-hook` (anything git or go does
   there as root leaves root-owned files that break the next hook build).
2. **Env files.** `cp infra/<host>/etc/*.env /srv/<env>-proto/etc/`, fill
   every `SERVERONLY`, set owner/mode as the header of each file says.
   Secrets and database passwords are generated on the host
   (`openssl rand -hex 32`) straight into the files.
3. **Postgres roles and the database.** `infra/sql/proto-host-db.sql`
   (`doc/340-db-host-setup.md`), one idempotent file with the passwords
   from step 2 on psql's stdin: `db_reader`/`db_writer`, `proto_ddl`
   (owns the database and schema; only `proto-migrate` connects as it —
   `etc/<env>-proto-migrate.env`), `proto_app` (DML only — the API,
   `etc/<env>-proto-api.env`), and on UAT `proto_ci` (`CREATEDB`, scratch
   DBs only — `etc/uat-proto-test.env`). `CONNECT` on the real database is
   revoked from `PUBLIC`, so the CI role cannot reach it.
4. **The data.** The runbooks restore a local `pg_dump --no-owner` as
   `proto_ddl` (`pg_restore --role`). An empty database instead gets its
   schema from the first deploy's `proto-migrate up`.
5. **Scripts and units.** `cp infra/<host>/bin/* /srv/<env>-proto/bin/ &&
   chmod +x`; `cp` the `.service`/`.path` files to `etc/`, symlink into
   `/etc/systemd/system`, `daemon-reload`, `enable --now
   <env>-proto-restart.path`, `enable <env>-proto-api`. The first deploy
   (`*-build` on UAT, `*-promote-uat-and-deploy` on prod) installs the
   binary and proves the path unit: `install-api` touches
   `stg/restart.request` and waits for `MainPID` to change. Do not touch
   it by hand before then: with no binary the unit fails, retries, and can
   hit its start limit (5 in 120 s) just as the install needs it.
6. **nginx + certs.** In this order, because the site names
   `crt/<site>/*.pem` and a site that fails `nginx -t` blocks every reload
   of the host's shared nginx: `etc/nginx_<site>` into `sites-available`
   (not linked yet); run `*-renew-web-certs` once by hand (`SITE_NAME`,
   `CERTBOT_EMAIL` in `deploy.env`); `ls -l crt/<site>` shows
   `fullchain.pem` root:www-data 0640 and `privkey.pem` root:root 0600;
   symlink into `sites-enabled`; `nginx -t && systemctl reload nginx`;
   then the script into root's cron.
7. **Webhook and monitoring.** Each `shrmpl-etc/` subdirectory into the
   matching one under `/srv/shrmpl/etc/` on the host that mirror belongs
   to, so UAT's monitors land on the monitoring host. Hooks: the real
   `HOOK_SECRET`, and `HOOK_ALLOWED_BRANCHES` must equal
   `BRANCH_TO_CHECKOUT`. Monitors: rename each `NACKID` to the check-in
   code the monitor is registered under and put
   the matching `https://<nackmon-host>/checkin?code=<nackid>` in
   `HEALTHCHECK_URL` / `CERT_HEALTHCHECK_URL`. Pulsecheck: `PULSE_URL` takes
   the real `SITE_NAME`. The webhooks and the build checkout's deploy key
   belong to the GitHub repository: a new repository needs them again
   (`doc/350-repository-reset.md`).
8. **fail2ban.** If `/etc/fail2ban/jail.local` is still a real file rather
   than a symlink, run `fail2ban/bin/migrate-to-srv-config` as root once.
   Then copy `fail2ban/etc/*` to `/srv/fail2ban/etc/`, fill `ignoreip`, and
   check the `/api/` exclusion against the live log with
   `fail2ban-regex /srv/<env>-proto/log/nginx_access.log
   /etc/fail2ban/filter.d/nginx-404.conf '"(GET|POST|HEAD) /api/'` (API
   lines show as ignored), then
   `fail2ban-client reload && fail2ban-client status <env>-proto`. On a host
   that already carries other apps, merge this repo's `[<env>-proto]` jail
   into the live file instead of overwriting it, and bring the merged result
   back here.
9. **Prod extras.** `prd-proto-backup-all` from root's cron with
   `etc/prd-proto-backup.env` (root:root 0600); `REMOTE_SERVER` is an ssh
   alias in root's `~/.ssh/config` and `REMOTE_DIR` must exist there. The
   script keeps `BACKUP_ROOT/prd-proto` root-only 0700 (the tarball holds
   `etc/`). Run it once by hand; `pg_restore --list <file>.dump` must list
   the schema.

## Deriving an app from this

The whole-repo procedure is `DERIVING.md`; `bin/000-rebrand <slug>` does
the `proto` → `<app>` rename here too (file names, contents, roles, nginx
upstream). What is left for a human on this tree: rename `infra/uat/` →
`infra/<real-uat-host>/` and `infra/prd/` → `infra/<real-prd-host>/`, add
the `infra/<host>/` bullet to the app's `CLAUDE.md` Layout section, and
adapt `doc/330` / `doc/331` to the real hosts. Nothing in `bin/` needs to
change for a new host — only `etc/`.
